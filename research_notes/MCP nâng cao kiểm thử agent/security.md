# Research notes: MCP security and agent testing

**Prepared:** 2026-11-20
**Scope:** Primary research and authoritative standards/repositories relevant to MCP tool-output injection, authorization and confused-deputy risks, process isolation, test artifacts, and adversarial protocol behavior. Research facts are separated from proposed controls and product inferences. Links were checked on 2026-11-20; fast-moving specifications and repositories should be rechecked before implementation.

## 1. What evidence says about tool-output prompt injection and agent-level risk

### Takeaway

Tool output is an attacker-controlled input channel for an agent. Published benchmarks show that injected instructions can redirect tool-using agents toward harmful actions or data exfiltration, but results depend on the tested models, tasks, defenses, and harness. A deterministic MCP regression run can preserve hostile output as test data and check server behavior; it cannot show whether an LLM follows or resists that text unless a separate agent harness actually runs the model and verifies its actions.

### Cited Findings

- **Greshake et al., “Not What You’ve Signed Up For: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection,” ACM AISec 2023** ([ACM paper](https://doi.org/10.1145/3605764.3623985), [arXiv version](https://arxiv.org/abs/2302.12173), [authors’ code](https://github.com/greshake/llm-security)). The paper demonstrates indirect injection through retrieved content in LLM-integrated applications and shows pathways to manipulate application behavior and API calls. This established the data/instruction trust-boundary problem before MCP-specific benchmarks. It is a collection of demonstrations and threat analysis, not a representative estimate of current MCP ecosystem risk.
- **Zhan et al., “InjecAgent: Benchmarking Indirect Prompt Injections in Tool-Integrated Large Language Model Agents,” Findings of ACL 2024 (August 2024)** ([ACL Anthology paper](https://aclanthology.org/2024.findings-acl.624/)). The benchmark contains 1,054 cases covering 17 user tools and 62 attacker tools; its attack goals include direct harm and private-data exfiltration. In their evaluated agents, ReAct-prompted GPT-4 was vulnerable in 24% of cases. Those rates describe the paper’s benchmark, prompts, models, and tested configuration, not all present-day agents.
- **Debenedetti et al., “AgentDojo: A Dynamic Environment to Evaluate Prompt Injection Attacks and Defenses for LLM Agents,” NeurIPS 2024 Datasets and Benchmarks Track** ([proceedings paper](https://proceedings.neurips.cc/paper_files/paper/2024/hash/97091a5177d8dc64b1da8bf3e1f6fb54-Abstract-Datasets_and_Benchmarks_Track.html), [ETH Zurich repository](https://github.com/ethz-spylab/agentdojo)). AgentDojo evaluates agents using tools over untrusted data and provides 97 tasks plus 629 security cases. Its authors report that state-of-the-art models can fail ordinary tasks even without an attack, and that attacks break some security properties but not all. This is evidence for measuring both security and task utility, rather than counting refusals alone.
- **Ruan et al., “Identifying the Risks of LM Agents with an LM-Emulated Sandbox” (ToolEmu), ICLR 2024** ([paper](https://openreview.net/pdf/d1601f78407737fc216de9e6ec0085038f8c885f.pdf), [authors’ repository](https://github.com/ryoungj/ToolEmu)). ToolEmu’s language-model emulator uses tool specifications and inputs to simulate tool effects rather than running the actual implementation. Human review judged 68.8% of the failures it identified to be valid real-world failures; its initial benchmark covers 36 toolkits and 144 cases. The authors explicitly frame this as scalable risk discovery with an emulated environment. It is useful for scenario ideation, but its emulated outcomes are not proof of the behavior or security of a real MCP server.
- **Zhang et al., “Agent Security Bench (ASB): Formalizing and Benchmarking Attacks and Defenses in LLM-Based Agents,” ICLR 2025** ([ICLR paper](https://proceedings.iclr.cc/paper_files/paper/2025/hash/5750f91d8fb9d5c02bd8ad2c3b44456b-Abstract-Conference.html), [authors’ repository](https://github.com/agiresearch/ASB)). ASB covers 10 scenarios, 10 agents, over 400 tools, 27 attack/defense methods and seven metrics. It evaluates prompt injection, memory poisoning, a plan-of-thought backdoor, mixed attacks, and defenses across 13 model backbones. Its reported maximum average attack success rate was 84.30% in its tested settings. This broad but benchmark-specific result must not be presented as a universal agent failure rate.
- **Khodayari et al., “Indirect Prompt Injection in the Wild: An Empirical Study of Prevalence, Techniques, and Objectives,” arXiv preprint (April 29, 2026)** ([paper](https://arxiv.org/abs/2604.27202)). The authors report analyzing 1.2 billion URLs across 24.8 million hosts, finding 15,300 validated injection instances across 11,700 pages; about 70% appeared in non-rendered HTML. In 5,200 controlled experiments across 13 models and four page representations, reported compliance reached up to 8% for smaller models on plain-text inputs, while structured representations reduced compliance. It is a preprint and concerns web content rather than MCP servers specifically; the figures support testing hidden/structured content formats, not a claim that every tool response is exploitable.

### Inferences

- Build a **safe output corpus** for the actual server fixture: benign output, direct override instructions, role impersonation, requests to reveal a canary secret, tool-call coercion, encoded/obfuscated strings, HTML comments/metadata, markdown/link content, multiline log-like text, and oversized payloads. Keep these as inert fixture bytes. Assert capture terminates as expected, secrets are not emitted to public text logs, and no secondary tool call occurs as a side effect of regression execution.
- Include tool-description and schema text in the same corpus. Research and OWASP describe injection/poisoning in descriptions, schemas, and return values; testing only `tools/call` output misses catalog-time attacks and tool-definition drift.
- If a future agent adapter is evaluated, use a separate opt-in harness with a fixed model/version, fixed tool set, disposable data, and scripted checks of tool calls and resulting state. Report attack success and benign-task utility separately, along with model/prompt/adapter identifiers. Reuse ideas and test scenarios from AgentDojo, InjecAgent, and ASB only after reviewing their licenses and current compatibility.
- Detection rules can flag suspicious content for review, but a clean detector result must not mean “safe”: OWASP states that pattern filters cannot establish that remaining tool text is safe, including against encoded or multilingual injections.

### Gaps

- The cited studies do not prove that a particular MCP server or agent is vulnerable. Most benchmark percentages are tied to specified model versions and scenario suites; model and harness updates can change them.
- `mcp-regress` is a local protocol/client regression gate, not an LLM agent red-team harness. It cannot claim prompt-injection resistance, correct agent intent interpretation, or safe downstream tool selection without actually running and inspecting those agents.
- Prompt-injection text cannot generally be made safe by a regex scrubber. The stronger boundary is authorization and validation in trusted application code for each consequential action, independent of model interpretation.

## 2. What MCP trust and permission boundaries require, including process isolation and artifacts

### Takeaway

MCP configuration is a trust decision: a local stdio server runs as a process with the client’s privileges, and a remote/proxy server can hold authority to downstream services. Tool annotations and descriptions are claims; least-privilege authorization, per-client consent, audience checks, and external isolation belong at the execution boundary. Snapshots and reports are also sensitive sinks: synthetic canaries and redaction checks should cover every persistence and display path.

### Cited Findings

- The **official MCP security policy** ([`modelcontextprotocol/modelcontextprotocol/SECURITY.md`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/SECURITY.md)) says clients trust servers they configure, local servers are trusted like installed software, and stdio command execution runs with the client’s privileges as an intended protocol behavior. It assigns server developers responsibility for access controls, documented permissions, input validation and least privilege; it assigns clients responsibility for consent and sandboxing where feasible. Therefore, “the client executed its configured server” is not by itself proof of a protocol vulnerability.
- The **official MCP Security Best Practices for the 2026-07-28 spec** ([spec repository page](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx)) explains confused-deputy risks when an MCP proxy acts on third-party APIs. It calls for per-client consent for proxy authorization, token audience validation, rejecting token passthrough, and separate downstream credentials; it also describes `state` validation and SSRF controls for OAuth discovery. Those controls primarily apply to remote OAuth/proxy deployments, not the project’s current local stdio profile.
- **OWASP MCP Security Cheat Sheet** ([MCP security guidance](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)) identifies tool poisoning and rug pulls, tool shadowing/cross-origin escalation, confused deputy, data exfiltration over legitimate calls, over-scoped permissions, supply-chain attacks, replay/tampering and sandbox escape as risk classes. It says to treat every tool response as untrusted; make sensitive actions subject to trusted authorization and often human approval; use least privilege; and do not treat output filtering as proof that the remaining content is safe.
- The **OWASP MCP Secure Development guide** ([GitHub guide](https://github.com/OWASP/MCP-Security-Testing-Guide/blob/main/04.%20Secure%20MCP%20Development.md)) describes tool output as a possible carrier of prompt injection, secrets, malicious links, oversized data and misleading content. It recommends output validation/labeling and size limits, secret scanning/masking, and tests for malicious tool descriptions and outputs. This is practical guidance, not an empirical measurement of the effectiveness of any one filter.
- The **OWASP Logging Cheat Sheet** ([logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)) recommends removing, masking, sanitizing, hashing or encrypting access tokens, passwords, connection strings, encryption keys and sensitive personal data rather than recording them directly. The OWASP MCP-specific guide also recommends redacting secrets and PII. For a regression tool, exact canary searches in all generated artifacts are a concrete validation of the product’s own redaction contract.
- **NIST SP 800-190, Application Container Security Guide (2017)** ([official publication](https://csrc.nist.gov/pubs/sp/800/190/final), [PDF](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-190.pdf)) describes container isolation as useful resource isolation while noting that a shared kernel has a larger inter-object attack surface than hypervisor isolation; insecure host-volume mounts can allow host file tampering. **gVisor’s official security architecture** ([design](https://github.com/google/gvisor/blob/master/g3doc/architecture_guide/security.md), [overview](https://gvisor.dev/docs/)) documents a sandbox boundary with a user-space application kernel and a restricted set of host interactions. These sources support an external isolation layer as an engineering control; they do not certify any specific CI setup.
- **Official MCP conformance framework** ([repository](https://github.com/modelcontextprotocol/conformance), [test server examples](https://github.com/modelcontextprotocol/conformance/tree/main/examples/servers/typescript)) performs wire-schema checks against a negotiated spec version and includes a deliberately vulnerable negative server for DNS-rebinding protection. This demonstrates a useful conformance-testing pattern: named adversarial fixtures with expected failures. Its checks are protocol conformance evidence, not a complete security assessment.

### Inferences

- For stdio, preserve the existing rule that the configured executable is trusted code. Keep env clearing as a defense against accidental inherited secret exposure, but document clearly that it is not a sandbox: it does not restrict filesystem access, network access, explicitly passed secrets, CPU or memory. Run untrusted servers in a disposable CI worker or a separate OS/container/VM policy with no production credentials, narrow mounts, disabled network where feasible, and explicit CPU/memory/time limits. Evaluate a maintained sandbox runtime or VM for the project; process groups and Windows Job Objects improve cleanup but do not limit what a still-running process may access.
- The server’s `readOnlyHint`/effect metadata can be tested as a policy input but not trusted as a proof of harmless behavior. A high-confidence read-only fixture needs a disposable state store and a before/after assertion. For every mutating test, use synthetic accounts/state, explicit opt-in, and cleanup assertions; record that cleanup can fail or be interrupted and cannot undo irreversible external effects.
- Add canary values to fixture responses, tool descriptions/schemas, call arguments, error strings, URLs and subprocess stderr. After a run, scan console output, Markdown, JSON, snapshots, test logs and temporary artifacts. Verify restrictive file permissions and alias/path behavior. Keep private full reports clearly private and minimize default public output to structured failure metadata, hashes, source/path identifiers and counts rather than full tool content.
- For remote OAuth support, create isolated tests for invalid audiences, token passthrough, cross-client consent, missing/replayed `state`, scope escalation, redirect/SSRF/private-IP targets and credential leakage. Run only against owned test infrastructure, never against arbitrary public MCP endpoints.
- Treat a changed tool definition as a policy review event (rug-pull detection), not merely informational text drift. Compare stable fields including tool name, schema, description, annotations and output schema; retain the exact diff as review evidence, but avoid blindly ingesting hostile descriptions into an agent prompt.

### Gaps

- Container/process controls are deployment-specific and can be misconfigured. Even an isolated container shares a kernel; a VM or stronger sandbox still needs careful credential, network, volume and runtime policy.
- `mcp-regress` cannot prove that fixture effect labels match real-world tool behavior. It can verify observed state changes only where the fixture controls a test environment and has an oracle.
- No source cited here proves that secret scanning can find every credential in arbitrary free text. Key-based redaction and exact canaries are useful tests but do not establish complete secret removal.
- Official MCP OAuth guidance is versioned and evolving. Re-check the exact spec revision and SDK behavior before supporting any newer auth lifecycle; do not infer HTTP/OAuth conformance from stdio test evidence.

## 3. What can be regression-tested deterministically, and what mcp-regress can claim

### Takeaway

There is a valuable, deterministic layer between “capture a baseline” and “prove an agent is safe”: exercise the real server against a versioned malicious-input corpus, assert bounded and correctly correlated protocol behavior, compare catalog/security metadata to a reviewed baseline, and verify artifact privacy. Report each result as evidence about one configured server, profile, fixture and run. The gate must not collapse protocol conformance, semantic authorization, operating-system isolation and LLM-agent robustness into one “secure” pass.

### Cited Findings

- **MCPGuard, “Finding Conformance Gaps in MCP SDKs via Dual-Track Analysis and Dynamic Adjudication,” arXiv preprint submitted August 12, 2026 and marked under review** ([paper](https://arxiv.org/abs/2611.03662)). The paper reports confirmed gaps in the official Python 1.26.0 and TypeScript 1.29.0 SDKs and says its generated structural PoCs reproduced 27 findings; five behavioral findings remained after full-context review and targeted probes. Its authors report that two black-box conformance baselines did not expose those findings, because SDK model enforcement can differ from endpoint behavior and a client SDK may block malformed inputs before they reach the target. The work is a recent under-review preprint; its claims and affected SDK versions should be labeled accordingly. It supports combining endpoint tests with schema/rule-specific negative probes, not replacing official conformance tests.
- **The official MCP conformance repository** ([README](https://github.com/modelcontextprotocol/conformance/blob/main/README.md)) tests clients and servers, captures protocol interactions, checks wire JSON Schema per negotiated spec revision, supports expected-failure baselines, and distinguishes required checks from optional/draft scenarios. The README explicitly notes that a passing score applies to its selected requirement set and suite, not every possible behavior. The project should pin the profile and record its interoperability evidence rather than claim a general “MCP compliant” status.
- **ToolEmu** (ICLR 2024; above) provides a contrasting test layer: an LM can cheaply emulate tools and explore long-tail scenarios, but emulator fidelity is approximate. Its own human review result (68.8% of flagged failures judged valid) shows why those outputs are candidates for review, not deterministic evidence about actual server behavior.
- Current project evidence lives in [`docs/SECURITY.md`](../../docs/SECURITY.md), [`docs/BACKLOG.md`](../../docs/BACKLOG.md), and [`docs/COMPATIBILITY.md`](../../docs/COMPATIBILITY.md). The project records a local stdio client that is not a sandbox; clean child environment is opt-in; recursive key-based redaction is implemented but free-text scanning remains open; process cleanup and bounded output/run controls are partial; only the `2025-06-18` profile is implemented; one bounded public-server interoperability run exists; and tool annotations/effect declarations are not proof of semantics. Backlog links include `CORE-02`, `CORE-03`, `CORE-05`, `DATA-02`, `FIX-01`, `HTTP-02`, and `AGENT-02`.

### Inferences

Suggested acceptance-oriented test families, aligned with the current backlog:

1. **Protocol-negative corpus (`CORE-02`, `CORE-03`):** malformed JSON, wrong JSON-RPC version, missing fields, wrong response ID, invalid result/error shape, unexpected methods, invalid negotiation/version, pagination loops, malformed schemas/content blocks, empty/truncated frames, overlong frame, many small frames, huge catalog/page, timeout, and server stderr flood. Use a fake local server and assert bounded memory/output/time, useful categorized errors, no secret/full-frame dump, and no snapshot promotion after any transport/protocol failure. Add each failing case as a fixed regression fixture with a reason.
2. **Hostile catalog/output corpus (`DATA-02`, `DIFF-02`, `UX-01`):** tool description/schema with “ignore previous instructions” or fake role headers, misleading `readOnlyHint`, mutating/destructive hints, output schema changes, control characters, bidi/unicode confusables, HTML comments, Markdown links/images, fake log lines, token-shaped strings and known canaries. Assert deterministic diff rules, untrusted-content labeling where shown, payload-free default human reports, and that the regression runner itself never interprets output as commands.
3. **Authorization and side-effect oracle (`FIX-01`, later `HTTP-02`):** in a disposable fixture server, invoke allowed, denied, wrong-scope and cross-user cases; use before/after state snapshots to prove actual mutation or lack thereof; test cleanup after setup failure, case failure, timeout and cancellation. Keep the test identities nonproduction. A textual “read-only” annotation alone is not a successful authorization test.
4. **Artifact secrecy and file safety (`DATA-01`, `DATA-02`):** place unique synthetic canaries across tool metadata, arguments, response strings, error data, URL fields and stderr. Run capture, replay, diff and check; scan generated files and console streams for canaries; assert output mode/permissions, atomic-write behavior, no path aliasing, and that a corrupted checksum is rejected. Record limits: canary scanning only proves those exact values were absent.
5. **Process containment (`CORE-02`, `CORE-05`):** controlled child/grandchild that hangs, forks, floods stdout/stderr, ignores SIGTERM, creates a new Unix session, or leaves files. Assert deadline/cancellation and cleanup semantics on each supported OS. Keep any deliberate escape experiment inside a disposable test machine; the runner should not describe process termination as sandboxing.
6. **Separate agent evaluation (`AGENT-01`, `AGENT-02`):** if the product later runs an agent, publish a distinct optional suite built from benchmark-inspired attack/task pairs with a fixed tool-call and state oracle. Keep model behavior claims separate from MCP wire checks. Record exact model version, prompt and tool metadata because those inputs affect reproducibility.

Each machine-readable result should include the server identity/version or binary digest where available, protocol profile, tool-catalog digest, fixture-set version, config digest excluding secrets, OS/runtime, run timestamp, check IDs and sanitized evidence. Store raw tool exchanges only when explicitly requested and in a private artifact. Baseline promotion should remain a reviewed, separate operation from the CI job that verifies the baseline.

### Gaps

- The local checker can establish only that the target produced observations matching specified rules under the checked fixture, process configuration, protocol profile, and time window. It cannot infer hidden server behavior, prove all states/inputs are safe, establish authorization policies that are not exercised, or certify third-party SDK internals.
- Static comparison of tool descriptions, schemas and annotations identifies changes and suspicious content, but not malicious intent or actual effect. Conversely, no detected change does not rule out server binary/dependency drift, dynamic behavior, hidden resource state, or compromised runtime.
- A deterministic server corpus does not test an LLM’s interpretation of those bytes. Model versions, agent framework, system prompts, memory, tool selection, UI confirmation and application authorization need a separate, controlled evaluation.
- A green protocol regression gate is not a penetration test, supply-chain review, data-protection audit, sandbox attestation, full MCP revision conformance result, or certification. State the exact profile and tested criteria in every public claim, and maintain independent conformance runs before claiming agent or protocol-version interoperability.
